## 日常迭代 （bug 修复 + 历史版本需求）

|   |   |   |
|---|---|---|
|阶段|动作||
||||
|bug/需求 提出|技术支持:<br><br>- 客户发起的bug要及时流转到测试身上。未流转过来的bug 不处理。||
|开发|开发：<br><br>- 从对应迭代的大版本分支 拉取开发分支进行开发。<br>    <br>- 开发&自测完成后，及时将流程流转到测试中||
|迭代立项|测试：<br><br>- 在工程效率建一个迭代（可以根据迭代进度选择是否建）|可以配置迭代计划，自动选择产品的版本按需自动创建迭代。|
|开始迭代|测试:<br><br>将今日所有提测中的需求统一关联到日迭代中。||
|提测|开发：<br><br>1. 将代码合并到对应的需求分支上<br>    <br>2. 提交MR 到 迭代分支，检查后合并MR<br>    <br>3. 部署到测试环境进行冒烟测试（可选）<br>    <br>4. 云效的状态流转到测试中<br>    <br>5. 如果测试未通过，则在feature 分支上更改后重新新提MR 。<br>    <br><br>测试：<br><br>1. 统一发起提测单，构建制品并发布到测试环境测试。<br>    <br>2. 更新云效工作项状态。|发起提测单会自动将所有需求合并到迭代分支上，如果需求有冲突则会提醒开发解决冲突。<br><br>如果冲突没有解决，则提测单无法通过。|
|出包|测试：<br><br>1. 填写测试报告<br>    <br>2. 确认最终的制品（制品与提测单是绑定的，选择的是某一此提测单打包出来的制品）<br>    <br>3. 更新后续云效状态。||
|发布|交付/技术支持/客服：<br><br>1. 填写发布单。<br>    <br>    运维：<br>    <br>2. 根据发布单填写的制品信息，发布代码。||

规则：

- 每个大版本只能有一个同时进行中的迭代，当天要出包的 需求/bug 都走这个迭代。
    
- 日迭代 的周期为 每个维护中的大版本每天一个，默认测试只测在昨日结束前(今日0 点前)到达测试中的bug/需求。如果当日有需求临时需要添加到此次迭代，必须在12:00 之前告诉测试，测试会加入到此次迭代计划中。日迭代 17:00 之后会发包，迭代会关闭。
    

## 关注重点

产品：

- 对迭代进行规划，在工程效率平台发起迭代。
    
- 完成需求初步评估、推进开发对需求进行初步评估，填写预估工时。
    
- 确认迭代工作项 和 计划提测、出包/发布 时间。
    

开发：

- 需求新增开发预评审环节，开发需要提前拆解任务评估需求工时。并及时将云效节点更改。
    
- 迭代需求开发完成后，必须将需求对应的代码提交/合并到对应的feature/fix 分支。
    
- 往迭代release 分支合并时，必须提交PR。
    
- 因为同时一个版本只会有一个迭代，所以此次迭代如果发不上去，就要撤销需求，走下一次迭代。
    
- 迭代开始后，对应的开发分支会钉钉通知到开发负责人，请注意查看。
    

测试：

- 关注迭代提测进度，到达项目提测时间，发起提测单
    
- 管理提测单，确保迭代发布的需求都有提测单关联
    
- 管理日迭代，对昨日提测中的需求关联到当日迭代中。当日发布的需求/bug都走日迭代。
    
- 提交最终的测试报告，确认最终迭代制品。
    

运维：

- 关注发布单的制品，根据制品进行发布。
    

待做

- 需要提供只构建制品+运行自动化测试的流水线
    
- 测试落地执行每日迭代在线化。
