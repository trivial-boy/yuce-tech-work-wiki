
## 1. 背景与目标

### 1.1 现状问题

当前 KA 项目的分支管理和发布流程依赖人工操作，存在以下核心痛点：

| 问题                | 现状                          | 影响                           |
| ----------------- | --------------------------- | ---------------------------- |
| **测试与发布制品不一致**    | 发布时需重新打包，测试到发布之间的过程不可控      | 线上实际运行的代码可能与测试验证的不一致，引发线上事故  |
| **代码合并易出错**       | 提测时手动合并代码到测试分支，无自动化保障       | 容易遗漏变更或合错分支，增加测试返工成本         |
| **发布信息不可追溯**      | 迭代版本缺乏统一的变更记录和分支管理          | 出现问题时难以定位某次发布包含了哪些需求和 Bug 修复 |
| **跨版本 Bug 修复效率低** | 同一 Bug 影响多个版本线时，各版本代码合并比较混乱 | 容易因为结构变更导致无法合并或者遗漏某个版本线      |

### 1.2 目标

| 目标               | 说明                                        |
| ---------------- | ----------------------------------------- |
| **测试制品即发布制品**    | 测试通过的制品直接用于发布，杜绝二次打包带来的不一致风险              |
| **版本可追溯**        | 每个迭代版本有清晰的变更记录、关联的分支和对应的制品                |
| **需求/Bug 记录可追溯** | 需求和 Bug 均关联到迭代版本，可追溯到具体版本的变更内容            |
| **跨版本 Bug 快速广播** | 已修复的 Bug 可按需一键广播到其他受影响的版本线，冲突时自动通知对应开发者处理 |

## 2. 分支模型设计

### 2.1 分支类型总览

| 分支类型  | 命名规范                         | 示例                                  | 生命周期 | 用途                    |
| ----- | ---------------------------- | ----------------------------------- | ---- | --------------------- |
| 大版本分支 | `release/{大版本号}`             | `release/v3.48`                     | 永久   | 已发布稳定版本的长期维护主线，承接后续补丁 |
| 迭代分支  | `release/{版本号}`              | `release/3.48-1`                    | 迭代周期 | 迭代发布代码，合并已验证的 feature |
| 需求分支  | `feature/{版本号}/{开发者}/{需求编号}` | `feature/3.56-1/zhangsan/user-auth` | 迭代周期 | 单个需求的开发分支             |
| 缺陷分支  | `fix/{版本号}/{开发者}/{bug编号}`    | `fix/3.56-1/lisi/BUG-1234`          | 迭代周期 | 单个 Bug 的修复分支          |

### 2.2 分支关系图

```
release/v1 (v1 长期维护线)
├── release/v1.1
│       ├── feature/v1.1/zhangsan/REQ-001
│       └── fix/v1.1/lisi/BUG-002
├── release/v1.2
│       ├── feature/v1.2/zhangsan/需求A
│       └── fix/v1.2/wangwu/BUG-003

release/v2 (v2 长期维护线)
├── release/v2.1
│       └── fix/v2.1/...
```

### 2.3 分支维护规则

**各分支定位：**

| 分支             | 定位             | 要求                            |
| -------------- | -------------- | ----------------------------- |
| 大版本分支          | 维护稳定代码         | 只接受已发布验证的代码合入。P0级bug 可以直接合入。  |
| 迭代分支           | 维护正在测试或准备发布的代码 | 最终态必须是本次准备发布的代码；未完成的需求在发布前须回退 |
| feature/fix 分支 | 单个需求/Bug 的开发分支 | 不允许包含与该需求无关的提交                |

**详细规则：**
1. **大版本分支长期维护**：迭代完成后，迭代分支统一合并到大版本分支并打 tag
2. **迭代分支跟随迭代生命周期**：P0 以下 Bug 每日新增一个迭代分支，在当日迭代分支上统一测试和发布；P0 级 Bug 从大版本分支单独拉分支快速修复
3. **发布走迭代分支**：若有需求已合并到迭代分支但未达到可发布状态，须从迭代分支回退该需求代码后方可发布
4. **feature/fix 分支与迭代生命周期一致**：迭代发布后删除分支；若需求延期，分支保留，关联到下个迭代时将代码合并到新迭代的开发分支中

## 3. 开发完整流程

### 3.1 正常流程

1. **创建迭代 → 创建迭代分支**
   - 若为新大版本号，创建大版本分支 `release/{大版本号}`（例：`release/3.54`）
   - 基于大版本分支创建迭代分支 `release/{版本号}`（例：`release/3.56-1`）

2. **开始迭代 → 创建开发分支**
   - 基于迭代分支创建开发分支，命名为 `{类型}/{版本号}/{开发者}/{工作项编号}`（例：`feature/3.56-1/lxx/oc-1111`）
   - 将分支名回填到云效工作项的自定义字段

3. **提测 → 合并到迭代分支并部署测试环境**
   - 将对应 feature/fix 分支合并到迭代分支

4. **测试完成出包 → 确认迭代分支完整性**
   - 最终出包时，需将大版本分支最新代码拉取到迭代分支；若引入新提交，将对应工作项关联到本次迭代

5. **验证通过 → 合回大版本分支**
   - 将迭代分支合并到大版本分支，并对本次迭代打 tag

### 3.2 异常流程

6. **需求延期 → 代码回退并重新构建制品**
   - 该需求本次不发布：在迭代分支上回退对应代码，重新部署到测试环境
   - 测试二次验证测试环境无误后，提交最终制品

7. **P0 级 Bug 紧急修复**
   - 从大版本分支拉取最新代码创建 bugfix 分支，可直接合并到 release 进行部署
   - 紧急修复完成后，将工作项关联到最新的迭代版本上

### 3.3 环境部署规则

- 一个迭代必须有一个独立的测试环境；正常情况下同一大版本不会有多个迭代并行，如有则合并到同一迭代
- P0 级 Bug 修复不能直接使用迭代环境进行测试，必要时协调运维提供独立机器

## 4. 自动化流程

### 4.1 创建迭代 → 创建迭代分支

**前置条件**：创建迭代时需选择大版本号，若为新版本则先创建版本号。

**触发动作**：创建新迭代

**自动化流程**：
1. 若为新大版本号，自动创建大版本分支 `release/{大版本号}`
2. 基于大版本分支创建迭代分支 `release/{版本号}`（如 `release/3.56-1`）
3. 将分支信息记录到迭代元数据中
4. 触发 Jenkins 部署该分支

**结果**：迭代详情页显示关联的 release 分支信息。

### 4.2 开始迭代 → 创建开发分支

**触发动作**：点击"开始迭代"按钮

**自动化流程**：
1. 根据工作项类型确定分支前缀（`feature` 或 `fix`）
2. 基于迭代分支创建开发分支，命名为 `{类型}/{版本号}/{开发者}/{工作项编号}`
3. 将分支名回填到云效工作项的自定义字段
4. 钉钉通知开发者：「你的开发分支已创建 → {分支名}」

### 4.3 提测 → 合并到迭代分支并部署测试环境

**触发动作**：工作项点击"提测"按钮 / 发起提测单

**自动化流程**：
1. 触发流水线，将对应 feature/fix 分支合并到迭代分支
2. 若合并冲突，钉钉通知对应开发者解决，解决后重新触发合并

**页面变更**：提测单显示测试环境发布进度，新增"重新部署"按钮。

### 4.4 迭代归档 → 合回大版本分支

**触发动作**：点击"迭代归档"按钮

**自动化流程**：
1. 将各 feature 分支逐一合并到大版本分支（每个 feature 合并时自动 squash 为单次提交）
2. 基于本次迭代合并的需求打 tag，并清理已完成的分支

## 5. Bug 修复场景

### 场景 A：为某个大版本修复紧急 Bug

1. 基于大版本分支创建修复迭代 
2. 单独发布一个环境进行测试，不能直接使用迭代环境
3. 上线验证后，将代码合并到

### 场景 B：同一 Bug 影响多个版本线

例如某 Bug 已在 `v1.1` 修复，但 `v2`、`v4` 也受影响。

**处理流程**：
1. 在源版本线（如 `v1`）完成首修，发布后得到 `delivery_commit_sha`
2. 在目标版本线（如 `v2`）创建修复迭代（如 `v2.1`）
3. 系统关联同一 Bug，并记录来源修复的 `delivery_commit_sha`
4. 系统自动尝试以下方式之一：
   - 自动 cherry-pick `delivery_commit_sha` 到目标迭代的新修复分支
   - 或创建 `fix/v2.1/{开发者}/{bug编号}` 并预填来源 commit 信息
5. cherry-pick 无冲突 → 直接进入提测
6. 存在冲突 → 通知开发者在目标版本线手动调整

**设计依据**：
- 同一个 Git 分支只能基于一个基线，不能跨版本线复用
- `v1` 上的修复未必能直接编译通过于 `v2` 或 `v4`
- 平台应复用"交付 commit"，而非强行共用同一开发分支

### 场景 C：新迭代需吸收旧版本的 Bug 修复

例如正在开发 `v4` 新迭代，同时 `v3` 修了一个 Bug，`v4` 也需要同步。

**处理流程**：
1. 在 `v3` 完成 Bug 修复并发布
2. 在 `v4` 迭代中关联该 Bug，标记为"需同步修复"
3. 系统基于 `delivery_commit_sha` 自动尝试同步到 `v4` 迭代分支
4. 同步成功 → 该 Bug 在 `v4` 迭代中直接进入提测
5. 同步失败 → 创建 `fix/v4.x/...` 分支由开发者手动调整

**结论**：平台中的"关联已有开发分支"应落地为"关联已有交付 commit / MR"，而非物理共用同一 Git 分支。

## 6. 延期需求处理

当某个需求需要从当前迭代延期到下个迭代时：

```
需求 B 延期到 3.56-2
       │
       ▼
不合并 feature/3.56-1/lisi/payment 到 release/3.56-1
       │
       ▼
基于 release/3.56-2 创建新分支：feature/3.56-2/lisi/payment
       │
       ▼
开发者在新分支上 cherry-pick 或 merge 旧分支代码
       │
       ▼
旧分支 feature/3.56-1/lisi/payment 标记为废弃
迭代完结时自动清理
```
