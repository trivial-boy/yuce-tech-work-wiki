#### 钉钉/飞书在线表格接入

**背景**：魔方平台需要将钉钉表格和飞书表格作为数据源接入，支持用户从在线表格直接导入数据。原有代码中，第三方 API 逻辑与业务逻辑高度耦合，SDK 直接调用散布各处，字段类型转换逻辑分散，导致代码难以维护、测试困难、扩展新数据源成本极高。

**我的行动**：没有直接在现有代码上堆叠功能，而是先梳理了现有数据源接入的调用链路，识别出核心问题是缺乏统一的抽象层。在此基础上：

- 设计并实现了统一的数据源适配层，将第三方 API 调用与业务逻辑解耦，新增数据源只需实现适配器接口即可接入
- 实现了在线表格字段变更检测功能，支持新增、删除、重复字段的策略化处理（自动新增/固定不增、任务失败/字段置空、任务失败/按序同步加后缀）
- 支持用户在数据接入时预览并选择字段，自动适配字段类型

**成果**：不仅完成了钉钉/飞书双数据源的接入，更从根本上解决了数据源扩展性问题，后续接入新的在线表格类型时开发成本大幅降低。

### 2.2 工程效率平台 — 工程规范与团队提效

![[Pasted image 20260414053337.png]]

**背景：**
	公司研发流程长期依赖人工串联，迭代管理、提测、发布、分支维护、环境部署等关键环节缺少统一线上化支撑，导致流程不透明、责任边界不清、状态不可追踪，且经常出现“测试通过但线上发布内容不一致”、“提测、部署依赖口头沟通"、”项目进度卡点难定位”等问题。
  **我的行动：**
	  不局限于“接到需求后做页面或接口”，而是从研发全流程视角出发，系统性梳理流程、沉淀规范，并推动工程效率平 建设，逐步将 KA 迭代管理、提测发布管理、构建部署链路标准化，口径收拢完成闭环。

![[Pasted image 20260414043522.png]]

 #### 1. KA 迭代流程 SOP 制定

  问题：KA 迭代需求堆积严重，流程节点多、参与角色多，但缺少统一标准，导致需求推进过程不透明，团队往往只能靠人工追问确
  认当前卡点。

  行动：梳理并设计了从需求提出到上线验证的完整状态流转，覆盖云效工作项全生命周期，明确每个节点的进入条件、输出物、责任角色和协作边界，形成标准化 SOP 文档并推动团队按统一口径执行。

  结果：将原本依赖经验和口头同步的流程，沉淀为可复用、可推广的标准流程，为后续平台化建设提供了统一业务规则基础，也显著提升了迭代过程的透明度和卡点定位效率
![[Pasted image 20260414043652.png]]

 #### 2.KA 迭代分支管理策略方案

![[Pasted image 20260414043615.png]]
  问题：现有分支管理方式较为混乱，测试与发布使用的代码和制品链路不统一，发布阶段往往需要重新打包，导致线上版本与测试验证版本存在不一致风险，影响交付质量和排障效率。

  行动：设计并制定了完整的分支管理模型，明确从迭代创建、开发协作、提测合并、版本归档到打 Tag 的完整链路，并覆盖 Bug 修复、延期需求、多迭代并行等复杂场景；同时配套设计自动化方案，为分支创建、合并校验、状态回显和归档打下基础。

  结果：统一了研发、测试、发布阶段的代码基线，降低了“测试通过但发布内容不一致”的风险，也让分支策略从“人工约定”升级 为“平台规则”，增强了流程稳定性和可执行性。

 #### 3. DevOps 平台持续集成
 ![[Pasted image 20260414043541.png]]


  问题：打包、发布流程过去主要依赖口头同步和人工触发，缺少统一的线上化管理。流水线执行结果与具体迭代、提测单缺乏关 联，每次构建产出的最终制品也没有统一记录口径，导致过程不可追踪、问题难复盘。在 KA 多版本并行推进的场景下，测试和部署机器也缺少统一管理，容易出现环境占用不清、资源浪费和版本混用的问题。
  
  行动：在工程效率平台中接入 Jenkins 流水线能力，围绕“提测、构建、部署”设计线上化流程；推动平台支持按产品、应用、机器维度配置部署链路，打通从迭代/提测单到流水线触发、状态回写、部署结果展示的闭环；同时结合云效 OpenAPI，逐步将代码仓库、分支、PR 等能力纳入平台统一管理。

  结果：显著提升了提测和部署环节的执行效率，减少了人工触发和环境冲突问题；将原本分散在 Jenkins、云效和人工沟通中的关键信息，沉淀到统一平台中，增强了过程可追踪性、问题定位效率和多产品线复用能力。


  #### 4. 工程效率平台产品化建设

  问题：研发流程中的很多动作虽然有规则，但缺少系统承载，导致规范难落地、状态难沉淀、执行质量依赖个人经验。

  行动：以平台化思路推进建设，将 SOP、分支策略、提测规则、部署动作从“文档约束”转化为“系统能力”；围绕迭代、工作项、提 测单、发布单、分支、部署记录等核心对象，逐步建立统一的数据模型和状态机制，推动流程信息线上沉淀，实现关键节点可视
  化、可追踪、可审计。

  结果：将原本零散的流程规则和人工协作方式，逐步固化为标准平台能力，降低了团队对个人经验的依赖，也为后续扩展自动化测试、发布审批、效率度量和流程优化提供了基础。

  
### 2.3 智能化机器人建设 — 前瞻性技术探索

搭建 OpenClaw 机器人平台，通过编写 Skill 提升企业智能化水平。目前已上线三个核心能力：

**1. 客户工单 Agent**

部署 OpenClaw Agent 并接入钉钉机器人通道，支持客户级别权限管控，实现 Bug 创建和需求创建的自动化 Skill。

**收益**：客户和交付团队可通过钉钉机器人自主提交需求和 Bug，减少了人工转录的沟通成本，提升了问题响应效率。

**2. 云效助手**

打通云效平台，支持通过机器人自动创建工单，让交付、客服团队能快速反馈问题，无需登录云效手动操作。同时支持定时统计需求状态，自动汇总每日工单信息推送给相关人员。

**收益**：问题反馈链路从"人工登录云效填写"缩短为"钉钉群内一句话创建"，需求状态每日自动同步，减少信息滞后和遗漏。

**3. 钉钉知识库 Skill**

封装钉钉知识库能力，支持查询项目内部知识库，记录日常客服文档和问题处理情况，沉淀群专属知识库。

**收益**：客服和交付人员可在群内直接检索历史问题解决方案，减少重复咨询，逐步积累形成项目级知识资产。

## 三、技术成长与方法论沉淀

### 3.1 AI 辅助开发模式的实践与总结

试用期内，在两个项目中分别实践了两种 AI 辅助开发模式，并形成了方法论总结：

**在 KA 魔方项目中 — TDD + AI 协作模式**

以飞书在线表格字段变更检测功能为例，实践了完整的 TDD + AI 开发流程：

1. **需求拆分**：利用 AI 协助将复杂需求拆分为独立模块（字段变更检测、字段映射保存、字段映射编辑、数据读取适配）
2. **Red 阶段**：通过高质量 Prompt（包含项目结构、方法签名、测试场景等完整上下文），让 AI 生成 Spock 测试代码，覆盖正常、边界、异常场景
3. **Green 阶段**：人工实现最小化业务代码使测试通过
4. **Refactor 阶段**：在测试保障下重构代码，提取方法、分离关注点

**在工程效率平台项目中 — SDD（Spec-Driven Development）规范驱动开发**

通过 OpenSpec 先定义接口规范和数据模型，再基于规范文档驱动 AI 生成代码，确保团队协作中代码风格和结构的一致性。

- **规范先行**：通过 OpenSpec 定义清晰的接口规范和数据模型，使 AI 生成的代码天然符合团队约定，减少人工校对成本
- **AI 协作提效**：基于规范文档作为上下文，AI 可以生成结构一致、风格统一的代码，降低多人协作时的代码风格差异
- **可维护性保障**：规范化约束确保代码结构统一，新成员可以快速理解和接手项目，代码的长期可维护性和健壮性得到保障

**核心认知：**
- **TDD 是 AI 开发的质量安全网**：测试用例约束了 AI 生成代码的正确性边界，防止"看起来对但逻辑错"的问题
- **SDD 是 AI 开发的项目规约**：规范文档约束了 AI 生成代码的结构和风格，保证多人协作下的一致性

### 3.2 业务理解的深化

- 深入理解了 KA 产品的多版本并行交付模式和客户定制化需求的管理方式
- 掌握了云效工作项从需求提出到上线验证的全链路状态流转
- 理解了"测试制品即发布制品"对产品质量保障的核心价值 — 这直接驱动了分支管理策略方案的设计

### 3.3 从"写代码"到"改流程"的意识转变

入职初期的角色是功能开发者，但在实际工作中逐步意识到：很多问题的根因不在代码层面，而在流程层面。

- 发现分支管理混乱的根因是缺乏统一规范，而非开发者操作不当 → 输出分支管理策略方案
- 发现迭代需求堆积的根因是流程节点不透明、责任不清晰 → 输出迭代流程 SOP
- 发现测试与发布制品不一致的根因是流程设计缺陷，而非技术实现问题 → 推动工程效率平台建设

这种从问题表象追溯到流程根因的思维方式，是试用期最重要的成长之一。
