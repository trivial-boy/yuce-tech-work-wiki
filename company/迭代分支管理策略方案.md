
## 1. 背景与目标

### 1.1 现状问题

当前开发流程中，分支管理依赖人工操作，存在以下问题：

- 开发人员需要手动创建 feature/fix 分支，命名不规范
- 提测时需要手动合并代码到测试分支，容易遗漏或出错
- 发布时手动合并到 release 分支，流程不可追溯
- 多迭代并行时，分支管理混乱，容易合错分支
- 代码冲突发现滞后，缺乏及时通知机制

### 1.2 目标

1. **开发者只关心写代码**：分支的创建、合并、清理全部自动化
2. **版本可追溯**：每个迭代的代码变更有清晰的分支和 tag 记录
3. **风险可控**：冲突及时发现，发布内容可选择性控制

## 2. 分支模型设计

### 2.1 分支类型总览

| 分支类型  | 命名规范                           | 示例                                  | 生命周期     | 用途                         |
| ----- | ------------------------------ | ----------------------------------- | -------- | -------------------------- |
| 大版本分支 | `release/{大版本号}`               | `release/v3.56`                     | 永久       | 已发布稳定版本的长期维护主线，用于承接该版本后续补丁 |
| 迭代分支  | `release/{版本号}`                | `release/3.56-1`                    | 迭代周期     | 迭代发布代码，合并已验证的 feature      |
| 需求分支  | `feature/{版本号}/{开发名拼音}/{需求编号}` | `feature/3.56-1/zhangsan/user-auth` | 数天 \~ 2周 | 单个需求的开发分支                  |
| 缺陷分支  | `fix/{版本号}/{开发名拼音}/{bug编号}`    | `fix/3.56-1/lisi/BUG-1234`          | 数天       | 单个 bug 的修复分支               |
|       |                                |                                     |          |                            |

### 2.2 分支关系图
```
release/v1 (v1 长期维护线)
├── release/v1.1 
│       ├── feature/v1.1/zhangsan/REQ-001
│       └── fix/v1.1/lisi/BUG-002
├── release/v1.2
│       ├── feature/v1.2/zhangsan/需求A
│       └── fix/v1.2/wangwu/BUG-003
│
release/v2 (v2 长期维护线)
├── release/v2.1
│       └── fix/v2.1/...

```

### 2.3 分支维护规则

- **迭代分支的基线**：统一基于对应大版本维护分支 `release/{大版本号}` 拉取。

**关键原则**：
1. `release/{大版本号}` 才是版本长期维护的真实主线，`release/{小版本号}` 只是一次迭代交付快照
2. 迭代交付后，要将对应迭代版本号 release/{小版本号} 合并回 `release/{大版本号}` 并打上tag。
3. 已发布旧版本的修复，**先回所属版本线**，再根据影响范围向其他版本线传播。

## 3. 完整生命周期流程

### 3.1 阶段一：创建迭代，创建迭代分支
**前置工作：** 迭代创建时要选择大版本号，如果是新版本则创建新版本号。
**触发动作**：创建新迭代，
**自动化动作**：

```
1. 创建大版本号时会生成一个大版本分支
2. 从大版本分支创建 迭代 release/{版本号}（例：release/3.56-1） 分支
3. 将分支信息记录到迭代信息中
4. 触发jekins 部署该分支
```

**结果**：
- 迭代详情页显示关联的 release 分支信息。

### 3.2 阶段二 开始迭代，创建开发分支

**触发条件**：开始迭代后
**自动化动作**：
```
1. 根据工作项类型确定分支前缀（feature 或 fix）
2. 从 release/{小版本号} 拉取分支
3. 分支命名：{类型}/{版本号}/{开发者用户名}/{工作项编号}
4. 将分支名回填到云效工作项的自定义字段中
5. 钉钉通知开发者：你的开发分支已创建 → {分支名}
```

### 3.3 阶段三：提测，自动合并到迭代分支并发布到测试环境

**触发条件**：
1. 工作项手动点击提测按钮
**自动化动作**：
```
1. 自动触发流水线 将对应feature/bug 分支合并到 小版本 分支
2. 如果合并冲突，钉钉通知对应同学解决冲突，解决完成后继续触发合并
```
对应页面变更：
提测单显示测试环境发布进度，新增重新部署按钮。

### 3.4 阶段四：发起提测单，合并大版本分支代码到当前迭代分支。

**触发条件**：点击 迭代归档 按钮。

**自动化动作**:
```
1. 自动将feature 合并到大版本上
2. 
```
### 3.5 阶段五：收尾 —— 打 Tag 并清理分支

**触发条件**：

**自动化流程**：

```
                迭代完结
                   │
                   ▼
        release/{版本号} 合并回 release/{大版本号}
                   │
                   ▼
        在目标长期分支上打 tag: v{版本号}
        （tag message 包含迭代信息摘要）
                   │
                   ▼
        清理分支：
        - 删除 release/{版本号}
        - 删除 test/{版本号}
        - 删除所有已合并的 feature/fix 分支
        - 未合并的 feature/fix 分支保留（标记为延期）
                   │
                   ▼
        钉钉通知：迭代 {版本号} 已完结
        附带 tag 信息和延期工作项列表
```

**Tag 信息格式**：

```
Tag: v3.56-1
Message:
  迭代：3.56-1
  发布时间：2026-04-01
  包含需求：
    - 需求A (feature/3.56-1/zhangsan/user-auth)
    - BUG-001 (fix/3.56-1/wangwu/BUG-001)
  延期需求：
    - 需求B → 转移至 3.56-2
```

**说明**：

- 对于 `v1 / v2 / v3` 这类长期维护版本，tag 应打在对应 `release/{大版本号}` 上
- 文档不再保留 `main` 分支模型，所有发布归档都回对应的大版本维护分支
- 如果其他大版本也需要同一修复，通过跨版本传播处理，不通过统一主干兜底

### 3.6 特殊场景：Hotfix 与跨版本修复

**触发条件**：已发布版本出现线上紧急问题

#### 场景 A：为某个已发布 LTS 版本修复

```
1. 在平台创建 hotfix 类型迭代：
   - version_line = v1
   - iteration_version = v1.1
2. 系统基于 release/v1 创建：
   - release/v1.1
   - test/v1.1
3. 每个 bug 创建单独分支：
   - fix/v1.1/{用户名}/{bug编号}
4. bug 分支提测后，自动合并到 test/v1.1
5. 测试通过的 bug 分支，发布时逐个合并到 release/v1.1
6. 发布完成后：
   - release/v1.1 合并回 release/v1
   - 在 release/v1 上打 tag：v1.1
   - 删除 release/v1.1 / test/v1.1 / 已完成 fix 分支
```

#### 场景 B：同一个 bug 还影响其他版本线

例如某个 bug 已在 `v1.1` 修复，但 `v2`、`v4` 也受影响。

**平台侧建议不要“复用同一个 Git 开发分支”**，而是复用**交付 commit**：

1. 在源版本线（如 `v1`）完成首修，并在发布时得到 `delivery_commit_sha`
2. 在目标版本线（如 `v2`）创建一个新的修复迭代（如 `v2.1`）
3. 系统为目标迭代关联同一个 bug，并记录“来源修复”为 `delivery_commit_sha`
4. 系统自动尝试两种方式之一：
   - 自动 cherry-pick `delivery_commit_sha` 到 `release/v2.1` 对应的新修复分支
   - 或自动创建 `fix/v2.1/{用户名}/{bug编号}`，并预填来源 commit 信息
5. 如果自动 cherry-pick 无冲突，可以直接进入提测
6. 如果存在冲突，再由开发者在目标版本线修正差异

**原因**：

- 同一个 Git 分支只能可靠地基于一个基线
- `v1` 上可编译的修复，未必能直接用于 `v2` 或 `v4`
- 平台应复用“交付 commit / 提交来源”，而不是强行复用“同一开发分支”

#### 场景 C：新功能迭代也需要吸收旧版本 bug 修复

例如正在做 `v4` 新迭代开发，同时 `v3` 上修了一个 bug，`v4` 也需要带上。

推荐流程：

1. 在 `v3` 的 hotfix 或常规迭代里完成修复
2. 在 `v4` 迭代中关联该 bug，标记为“需同步修复”
3. 系统基于 `delivery_commit_sha` 自动尝试同步到 `v4` 的迭代分支
4. 同步成功后，该 bug 在 `v4` 迭代里直接进入提测
5. 同步失败时，再创建或激活 `fix/v4.x/...` 分支做人工调整

**结论**：你平台里的“关联已有开发分支”更适合落成“关联已有交付 commit / MR”，而不是物理上共用同一个 Git 分支。

## 4. 延期需求处理

当某个需求需要从当前迭代延期到下个迭代时：

```
                需求B 延期到 3.56-2
                       │
                       ▼
          不合并 feature/3.56-1/lisi/payment 到 release/3.56-1
                       │
                       ▼
          基于 release/3.56-2 创建新分支：
          feature/3.56-2/lisi/payment
                       │
                       ▼
          开发者在新分支上 cherry-pick 或 merge 旧分支的代码
                       │
                       ▼
          旧分支 feature/3.56-1/lisi/payment 标记为废弃
          迭代完结时自动清理
```

如果当前迭代本身被废弃或重编号，则不能简单保留原 `release/{版本号}` 继续使用，而应执行以下标准迁移流程：

```text
1. 确认当前版本线最新已发布基线
   - 即 release/{大版本号} 当前最新提交
2. 基于该基线创建新的合法迭代分支
   - 例如从 release/v3 创建 release/v3.42
3. 为新迭代重新创建 test/{版本号}
4. 将被废弃迭代中的有效工作项逐个迁移到新迭代
5. 将原迭代中已开发的 feature/fix 分支变更 merge 或 cherry-pick 到新迭代对应分支
6. 原废弃迭代分支标记为 obsolete，不再允许继续发布
```

这样做的目的，是确保新的迭代分支始终建立在“最新已发布基线”之上，而不是继续依赖已经失效的旧迭代上下文。

## 5. 多迭代并行策略

KA 产品经常出现多个迭代并行开发的情况：

```
时间轴 →

3.56-1:  [开发] ──── [提测] ──── [发布] ──── [完结]
3.56-2:       [开发] ──── [提测] ──── [发布] ──── [完结]
3.57-1:            [开发] ──── [提测] ──── ...
```

### 5.1 并行规则

1. **同一大版本内**（如 3.56-1 和 3.56-2）：

   - 后续迭代基于前一迭代的 release 分支或当前版本线的长期分支拉取
   - 前一迭代发布后，后续迭代同步的是 `release/{大版本号}`

2. **跨大版本**（如 3.56-x 和 3.57-x）：

   - 各版本独立，互不影响
   - 新大版本首次启用时，先创建对应 `release/{大版本号}`，之后所有迭代都基于该分支拉取
   - 只有确认受影响的 bug，才通过 `delivery_commit_sha` 向其他版本线传播

### 5.2 长期分支的同步顺序

```
原则：先合回所属版本线，再决定是否向更高版本同步

release/v1.1 发布完成 → 合回 release/v1 → 打 tag v1.1
                             │
                             ▼
                 判断 v2 / v3 是否也受影响
                             │
                             ▼
              需要同步的版本线执行 cherry-pick / 传播分支
```

### 5.3 同版本线并行迭代的发布顺序

同一个版本线下，允许多个迭代并行开发、并行提测，但**发布顺序必须严格按版本号递增**。

以 `3.41` 和 `3.42` 为例：

1. `3.41` 和 `3.42` 可以同时存在，也都可以提测
2. 如果 `3.42` 已满足发布条件，而 `3.41` 还未准备好，`3.42` 也不能先发布
3. 此时只能二选一：
   - 将 `3.41` 迭代废弃或重编号，合并到新的后续迭代中
   - 先把 `3.41` 的需求或 bug 发布出去，再发布 `3.42`
4. 只要 `3.42` 作为 `3.41` 的后续迭代存在，`3.42` 的交付内容就必须包含 `3.41` 中所有确认要交付但尚未发布的工作项
5. 如果选择废弃或重编号 `3.41`，则不能直接拿当前 `3.42` 分支继续发布，而必须：
   - 基于最新已发布的版本线基线重新创建新的迭代分支
   - 再把当前 `3.42` 的迭代内容合并进新的分支
6. 迁移完成后，原 `3.41` 和旧 `3.42` 分支都应标记为 obsolete 或仅保留审计用途，不再作为正式发布分支

**原因**：

- 版本号应与真实交付顺序保持一致
- 同一版本线的交付记录必须严格单调递增，便于追溯、出包和问题定位
- 如果允许 `3.42` 先于 `3.41` 发布，会直接破坏版本号语义和平台自动化规则
- 如果 `3.42` 不包含 `3.41` 的内容，就会导致同一版本线的后续版本丢失前序迭代应有的变更
- 如果废弃低版本号后不重建高版本迭代分支，就可能把旧基线里的脏上下文继续带入后续发布

**推荐平台规则**：

- 同版本线的迭代状态允许并行：`开发中`、`测试中`
- 同版本线的发布序号必须单调递增
- 当存在更低版本号且未完结的迭代时，更高版本号迭代应禁止发起正式发布
- 当高版本迭代处于待发布状态时，系统必须校验其是否已吸收所有更低版本号迭代的待发布工作项
- 如果低版本号迭代不再发布，则必须先执行：
  - `废弃迭代`
  - 或 `重编号/转后续迭代`
- 在废弃后继续交付时，系统必须强制重新创建新的迭代发布分支与测试分支
- 只有在更低版本号迭代已发布或已废弃后，更高版本号迭代才可发布

**推荐结论**：

- `3.41` 必须先于 `3.42` 发布
- 如果 `3.41` 不发，就先废弃或重编号 `3.41`
- 废弃后需要基于最新已发布基线重建新的迭代分支，再把当前迭代内容合并进去
- `3.42` 作为后续迭代时，必须包含 `3.41` 的待发布需求和 bug

## 6. 与现有系统的集成设计

### 6.1 云效(Yunxiao)集成

| 触发事件 | 系统动作 |
| --- | --- |
| 工作项关联到迭代 | 自动创建 feature/fix 分支，分支名回填云效字段 |

| 工作项从迭代移除 | 标记分支为废弃（不自动删除，避免误操作） |

| 操作 | API |

| 删除分支 | Codeup API: DELETE /branches |
| 打 Tag | Codeup API: POST /tags |
| 监听 push | Codeup Webhook: push events |

### 6.3 钉钉通知

| 场景 | 通知内容 | 通知对象 |
| --- | --- | --- |
| 分支创建 | 你的开发分支已创建：{分支名} | 工作项开发者 |
| 合并成功 | {分支名} 已合并到 test/{版本号} | 工作项开发者 |

### 6.4 流水线集成

| 触发条件 | 流水线动作 |
| --- | --- |
| test 分支有新的 merge | 触发测试环境部署流水线 |
| release 分支有新的 merge | 触发发布流水线 |

## 7. 数据模型变更（概要）

需要在现有系统中新增以下数据模型支撑：

### 7.1 版本线 (VersionLine)

```text
- id
- product_id            → 关联产品
- name                  → 版本线名称，如 v1 / v2 / v3
- line_branch          → 长期维护分支名，如 release/v1
- source_tag            → 首次创建时的基线 tag
- support_level         → latest / lts / maintenance / deprecated
- status                → active / frozen / deprecated
- created_at
```

### 7.2 代码仓库 (CodeRepository)

```
- id
- product_id        → 关联产品
- name              → 仓库名称
- codeup_repo_id    → Codeup 仓库 ID
- branch_strategy   → pure-release-line
- created_at
```

### 7.3 迭代分支记录 (IterationBranch)

```
- id
- iteration_id      → 关联迭代
- version_line_id   → 关联版本线
- repo_id           → 关联代码仓库
- iteration_type    → feature / hotfix
- branch_type       → release / test
- branch_name       → 分支全名
- base_ref          → 基线（tag 名或分支名）
- status            → active / merged / deleted
- created_at
```

### 7.4 工作项分支记录 (WorkItemBranch)

```
- id
- work_item_id      → 关联工作项
- iteration_id      → 关联迭代
- version_line_id   → 关联版本线
- repo_id           → 关联代码仓库
- branch_type       → feature / fix
- branch_name       → 分支全名
- delivery_commit_sha → 发布进入 release 后的标准交付 commit
- source_commit     → 如果是跨版本复用，记录来源交付 commit
- merge_status      → pending / merged / conflict / skipped
- merge_attempts    → 合并尝试记录 (JSON)
- created_at
```

### 7.5 分支传播记录 (FixPropagation)

```text
- id
- work_item_id          → 关联 bug
- source_version_line   → 源版本线，如 v1
- source_commit         → 源交付 commit
- target_version_line   → 目标版本线，如 v2 / v4
- target_iteration_id   → 目标迭代
- propagation_mode      → cherry-pick / manual-branch
- status                → pending / success / conflict / skipped
- created_at
```

### 7.6 分支合并日志 (BranchMergeLog)

```
- id
- source_branch     → 源分支
- target_branch     → 目标分支
- merge_type        → to_test / to_iteration_release / to_version_line
- status            → success / conflict / failed
- conflict_files    → 冲突文件列表 (JSON)
- operator          → 操作人（自动/手动）
- created_at
```

## 8. 分支数量估算与清理策略

### 8.1 分支数量估算

假设：同时进行 2 个迭代，每个迭代 10 个工作项

```
活跃分支数 = 2 × (1 release + 1 test + 10 feature/fix) = 24 个
```

迭代完结后自动清理，活跃分支数保持可控。

### 8.2 自动清理规则

| 条件 | 动作 |
| --- | --- |
| feature/fix 分支已合并到 test 且测试通过 | 迭代完结时删除 |
| feature/fix 分支已合并到 release | 迭代完结时删除 |
| test 分支 | 迭代完结时删除 |
| 迭代 release 分支 | 合回 `release/{大版本号}` 并打 tag 后删除 |
| 版本线 release 分支 | 长期保留，不删除 |
| 废弃分支（需求延期/取消） | 迭代完结时删除 |
| 未合并的 feature/fix 分支 | 通知开发者确认后删除 |

---

## 9. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| Codeup API 不可用 | 分支操作失败 | 加入重试机制（3次重试），失败后降级为人工操作并通知 |
| 自动合并导致代码质量问题 | 测试环境不稳定 | test 分支仅用于测试，release 分支逐个合并已验证代码 |
| 多人同时解决冲突 | 冲突反复出现 | 加锁机制，同一时间只处理一个分支的合并 |
| 开发者直接在 test/release 分支上提交 | 分支管理混乱 | 通过 Codeup 分支保护规则禁止直接 push |
| 迭代版本号命名冲突 | 分支名重复 | 创建前校验，版本号全局唯一 |

## 10. 实施阶段建议

### 阶段一：基础分支管理

- 迭代创建时自动创建 release/test 分支
- 工作项关联迭代时自动创建 feature/fix 分支
- 分支信息回填到云效工作项字段

### 阶段二：自动合并

- 云效提测 webhook → 自动合并到 test
- 合并冲突钉钉通知
- 冲突解决后自动重试

### 阶段三：发布与收尾

- 发布时从 feature 逐个合并到 release
- 迭代完结时打 tag、清理分支、合回大版本维护分支

### 阶段四：增强

- Hotfix 流程
- 多迭代并行的自动同步
- 分支操作审计日志
- 分支保护规则自动配置
