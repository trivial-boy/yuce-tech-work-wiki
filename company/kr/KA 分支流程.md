# 迭代分支管理策略方案

> 状态：待评审
> 适用产品类型：KA（大客户定制交付）
> 关联系统：云效(Yunxiao) + Codeup + 钉钉通知

---

## 1. 背景与目标

### 1.1 现状问题

当前开发流程中，分支管理依赖人工操作，存在以下问题：

- 开发人员需要手动创建 feature/fix 分支，命名不规范
- 提测时需要手动合并代码到测试分支，容易遗漏或出错
- 发布时手动合并到 release 分支，流程不可追溯
- 多迭代并行时，分支管理混乱，容易合错分支
- 代码冲突发现滞后，缺乏及时通知机制

### 1.2 目标

1. **开发者只关心写代码**：分支的创建、合并、清理全部自动化
2. **版本可追溯**：每个迭代的代码变更有清晰的分支和 tag 记录
3. **风险可控**：冲突及时发现，发布内容可选择性控制
4. **分支不膨胀**：迭代完成后自动清理，历史版本通过 tag 归档

## 2. 分支模型设计

### 2.1 分支类型总览

| 分支类型 | 命名规范 | 示例 | 生命周期 | 用途 |
|---------|---------|------|---------|------|
| 主干分支 | `main` | `main` | 永久 | 稳定基线，所有发布最终合回此分支 |
| 迭代发布分支 | `release/{版本号}` | `release/3.56-1` | 迭代周期 | 迭代发布代码，合并已验证的 feature |
| 迭代测试分支 | `test/{版本号}` | `test/3.56-1` | 迭代周期 | 聚合提测代码，自动触发测试环境部署 |
| 需求分支 | `feature/{版本号}/{用户名}/{需求缩写}` | `feature/3.56-1/zhangsan/user-auth` | 数天 ~ 2周 | 单个需求的开发分支 |
| 缺陷分支 | `fix/{版本号}/{用户名}/{bug编号}` | `fix/3.56-1/lisi/BUG-1234` | 数天 | 单个 bug 的修复分支 |
| 热修复分支 | `hotfix/{版本号}/{描述}` | `hotfix/3.56-1/critical-fix` | 数小时 ~ 数天 | 已发布版本的紧急修复 |

### 2.2 分支关系图

```
main (稳定主干)
 │
 │  ← 迭代创建时，基于 main 最新 tag 拉取
 │
 ├── release/3.56-1 ──────────────────────────── → 发布后打 tag v3.56-1，合回 main，删除分支
 │    │
 │    └── test/3.56-1 ────────────────────────── → 发布后删除
 │         │
 │         ├── feature/3.56-1/zhangsan/需求A ── → 合并到 test 后删除
 │         ├── feature/3.56-1/lisi/需求B ────── → 合并到 test 后删除
 │         └── fix/3.56-1/wangwu/BUG-001 ───── → 合并到 test 后删除
 │
 ├── release/3.56-2 (可与 3.56-1 并行)
 │    └── test/3.56-2
 │         └── feature/3.56-2/...
 │
```

### 2.3 基线拉取规则

**迭代分支的基线**：基于 main 分支上**当前大版本的最新 release tag** 拉取。

规则细节：

1. 大版本号通过迭代版本号的前缀确定（如 `3.56-1` 的大版本为 `3.56`）
2. 创建 `release/3.56-2` 时，查找 main 上是否已有 `v3.56-1` 的 tag
   - 如果有 → 基于 `v3.56-1` tag 拉取
   - 如果没有（3.56-1 还未发布合回 main）→ 基于 `release/3.56-1` 的最新提交拉取
3. 如果是大版本的第一个迭代（如 `3.56-1`），基于 main 最新 tag 拉取

```
示例：

main ───[v3.55]───[v3.56-1]───[v3.56-2]───
              │         │
              │         └── release/3.56-2 基于此点拉取
              │
              └── release/3.56-1 基于此点拉取
```

## 3. 完整生命周期流程

### 3.1 阶段一：迭代创建

**触发条件**：在系统中创建新迭代，填写版本号（如 `3.56-1`）

**自动化动作**：

```
1. 确定基线提交点（按 2.3 规则）
2. 从基线创建 release/{版本号} 分支
3. 从 release/{版本号} 创建 test/{版本号} 分支
4. 将分支信息记录到迭代数据中
```

**结果**：创建完成后，迭代详情页显示关联的 release 和 test 分支信息。

### 3.2 阶段二：需求/Bug 分支创建

**触发条件**：工作项（需求/Bug）关联到迭代后

**自动化动作**：

```
1. 根据工作项类型确定分支前缀（feature 或 fix）
2. 从 release/{版本号} 拉取分支
3. 分支命名：{类型}/{版本号}/{开发者用户名}/{工作项缩写或编号}
4. 将分支名回填到云效工作项的自定义字段中
5. 钉钉通知开发者：你的开发分支已创建 → {分支名}
```

**关键决策 - 分支从哪里拉取**：

| 方案 | 从 release 分支拉取 | 从 test 分支拉取 |
|------|-------------------|-----------------|
| 优点 | 基线干净，不包含其他未验证代码 | 包含其他 feature 的代码，提前暴露冲突 |
| 缺点 | 提测合并时可能冲突更多 | 基线不纯净，可能引入其他 feature 的 bug |
| **建议** | **推荐** | 不推荐 |

> **推荐从 release 分支拉取**，保证每个 feature 分支的基线是干净的。

### 3.3 阶段三：提测 —— 自动合并到 test

**触发条件**：云效工作项状态变更为"提测"（通过云效 webhook 回调）

**自动化流程**：

```
                    云效状态变为"提测"
                         │
                         ▼
                  系统接收 webhook
                         │
                         ▼
              查找工作项关联的 feature/fix 分支
                         │
                         ▼
              自动执行 merge → test/{版本号}
                         │
                    ┌────┴────┐
                  成功        冲突
                    │          │
                    ▼          ▼
            记录合并结果    记录冲突信息
            更新工作项状态   │
                    │          ▼
                    ▼      钉钉通知开发者：
            自动触发        "你的 {分支名} 合并到
            流水线部署       test/{版本号} 时发生冲突"
            test 环境        附带冲突文件列表
                              │
                              ▼
                        开发者在本地：
                        git pull origin test/{版本号}
                        # 在 feature 分支上解决冲突
                        git push
                              │
                              ▼
                        系统监听 push 事件
                        自动重试合并
```

**冲突处理的关键设计**：

1. **冲突责任人**：始终是 feature/fix 分支的开发者
2. **开发者操作方式**：在自己的 feature 分支上 merge test 分支的代码，解决冲突后 push
3. **自动重试**：系统监听 feature 分支的 push 事件，发现该分支处于"待合并"状态时自动重试
4. **超时机制**：冲突超过 24 小时未解决，升级通知给迭代技术负责人
5. **合并记录**：每次合并（成功/失败/重试）都记录日志，可在系统中查看

### 3.4 阶段四：发布 —— 从 feature 逐个合并到 release

> 这是方案的核心安全机制：**test 分支是脏分支，不直接合并到 release。发布时从已验证通过的 feature 分支逐个合并到 release。**

**触发条件**：迭代发起发布

**自动化流程**：

```
                    发起发布
                       │
                       ▼
              获取本次迭代所有工作项
                       │
                       ▼
              筛选状态为"测试通过"的工作项
              ↓
              展示待发布的 feature/fix 分支列表
              由负责人确认发布范围
                       │
                       ▼
              逐个合并已确认的分支 → release/{版本号}
                       │
                  ┌────┴────┐
                全部成功    存在冲突
                  │          │
                  ▼          ▼
           自动触发       暂停发布
           发布流水线     通知相关开发者处理
                  │
                  ▼
            发布成功后
            继续阶段五
```

**为什么不从 test 合到 release**：

- test 分支包含所有提测的代码，包括测试未通过的、需要延期的需求
- 从 feature 逐个合并可以精确控制发布范围
- 某个需求临时不上线，只需在确认列表中排除，不影响其他需求

**发布范围确认清单示例**：

```
迭代 3.56-1 发布确认：

[x] feature/3.56-1/zhangsan/user-auth    需求A  测试通过
[x] fix/3.56-1/wangwu/BUG-001            BUG修复 测试通过
[ ] feature/3.56-1/lisi/payment           需求B  测试未通过 → 延期到下个迭代
```

### 3.5 阶段五：收尾 —— 打 Tag 并清理分支

**触发条件**：发布完成，迭代状态变为"已完结"

**自动化流程**：

```
                迭代完结
                   │
                   ▼
        release/{版本号} 合并回 main
                   │
                   ▼
        在 main 上打 tag: v{版本号}
        （tag message 包含迭代信息摘要）
                   │
                   ▼
        清理分支：
        - 删除 release/{版本号}
        - 删除 test/{版本号}
        - 删除所有已合并的 feature/fix 分支
        - 未合并的 feature/fix 分支保留（标记为延期）
                   │
                   ▼
        钉钉通知：迭代 {版本号} 已完结
        附带 tag 信息和延期工作项列表
```

**Tag 信息格式**：

```
Tag: v3.56-1
Message:
  迭代：3.56-1
  发布时间：2026-04-01
  包含需求：
    - 需求A (feature/3.56-1/zhangsan/user-auth)
    - BUG-001 (fix/3.56-1/wangwu/BUG-001)
  延期需求：
    - 需求B → 转移至 3.56-2
```

### 3.6 特殊场景：Hotfix

**触发条件**：已发布版本出现线上紧急问题

**流程**：

```
1. 从 tag v{版本号} 创建 hotfix/{版本号}/{描述} 分支
2. 在 hotfix 分支上修复
3. 修复完成后：
   - 合并到 main（并打新 tag，如 v3.56-1.1）
   - 合并到当前活跃迭代的 release 分支（如 release/3.56-2）
4. 删除 hotfix 分支
```

## 4. 延期需求处理

当某个需求需要从当前迭代延期到下个迭代时：

```
                需求B 延期到 3.56-2
                       │
                       ▼
          不合并 feature/3.56-1/lisi/payment 到 release/3.56-1
                       │
                       ▼
          基于 release/3.56-2 创建新分支：
          feature/3.56-2/lisi/payment
                       │
                       ▼
          开发者在新分支上 cherry-pick 或 merge 旧分支的代码
                       │
                       ▼
          旧分支 feature/3.56-1/lisi/payment 标记为废弃
          迭代完结时自动清理
```

## 5. 多迭代并行策略

KA 产品经常出现多个迭代并行开发的情况：

```
时间轴 →

3.56-1:  [开发] ──── [提测] ──── [发布] ──── [完结]
3.56-2:       [开发] ──── [提测] ──── [发布] ──── [完结]
3.57-1:            [开发] ──── [提测] ──── ...
```

### 5.1 并行规则

1. **同一大版本内**（如 3.56-1 和 3.56-2）：
   - 后续迭代基于前一迭代的 release 分支拉取
   - 前一迭代发布合回 main 后，后续迭代需要 merge main 以同步变更

2. **跨大版本**（如 3.56-x 和 3.57-x）：
   - 各版本独立，互不影响
   - 新大版本基于 main 最新 tag 拉取

### 5.2 合回 main 的顺序

```
原则：先发布的先合回 main

3.56-1 发布完成 → 合回 main → 打 tag v3.56-1
                       │
                       ▼
                  通知 3.56-2 需要同步 main
                       │
                       ▼
3.56-2 的 release 分支 merge main
```

如果 3.56-2 先于 3.56-1 发布（特殊情况）：
- 3.56-2 先合回 main，打 tag
- 3.56-1 发布后也合回 main，在合并前需要先 merge main

## 6. 与现有系统的集成设计

### 6.1 云效(Yunxiao)集成

| 触发事件 | 系统动作 |
|---------|---------|
| 工作项关联到迭代 | 自动创建 feature/fix 分支，分支名回填云效字段 |
| 工作项状态变为"提测" | 自动合并 feature/fix → test 分支 |
| 工作项从迭代移除 | 标记分支为废弃（不自动删除，避免误操作） |

### 6.2 Codeup 集成

| 操作 | API |
|------|-----|
| 创建分支 | Codeup API: POST /branches |
| 合并分支 | Codeup API: POST /merge_requests + merge |
| 删除分支 | Codeup API: DELETE /branches |
| 打 Tag | Codeup API: POST /tags |
| 监听 push | Codeup Webhook: push events |

### 6.3 钉钉通知

| 场景 | 通知内容 | 通知对象 |
|------|---------|---------|
| 分支创建 | 你的开发分支已创建：{分支名} | 工作项开发者 |
| 合并成功 | {分支名} 已合并到 test/{版本号} | 工作项开发者 |
| 合并冲突 | {分支名} 合并冲突，附冲突文件列表 | 工作项开发者 |
| 冲突超时 | {分支名} 冲突超过24小时未解决 | 迭代技术负责人 |
| 发布确认 | 请确认发布范围（附分支列表） | 迭代技术负责人 |
| 迭代完结 | 迭代已完结，tag 已打，附延期工作项 | 迭代相关人员 |

### 6.4 流水线集成

| 触发条件 | 流水线动作 |
|---------|-----------|
| test 分支有新的 merge | 触发测试环境部署流水线 |
| release 分支有新的 merge | 触发发布流水线 |

## 7. 数据模型变更（概要）

需要在现有系统中新增以下数据模型支撑：

### 7.1 代码仓库 (CodeRepository)

```
- id
- product_id        → 关联产品
- name              → 仓库名称
- codeup_repo_id    → Codeup 仓库 ID
- default_branch    → 默认分支（main）
- created_at
```

### 7.2 迭代分支记录 (IterationBranch)

```
- id
- iteration_id      → 关联迭代
- repo_id           → 关联代码仓库
- branch_type       → release / test
- branch_name       → 分支全名
- base_ref          → 基线（tag 名或分支名）
- status            → active / merged / deleted
- created_at
```

### 7.3 工作项分支记录 (WorkItemBranch)

```
- id
- work_item_id      → 关联工作项
- iteration_id      → 关联迭代
- repo_id           → 关联代码仓库
- branch_type       → feature / fix / hotfix
- branch_name       → 分支全名
- merge_status      → pending / merged / conflict / skipped
- merge_attempts    → 合并尝试记录 (JSON)
- created_at
```

### 7.4 分支合并日志 (BranchMergeLog)

```
- id
- source_branch     → 源分支
- target_branch     → 目标分支
- merge_type        → to_test / to_release / to_main / hotfix
- status            → success / conflict / failed
- conflict_files    → 冲突文件列表 (JSON)
- operator          → 操作人（自动/手动）
- created_at
```

## 8. 分支数量估算与清理策略

### 8.1 分支数量估算

假设：同时进行 2 个迭代，每个迭代 10 个工作项

```
活跃分支数 = 2 × (1 release + 1 test + 10 feature/fix) = 24 个
```

迭代完结后自动清理，活跃分支数保持可控。

### 8.2 自动清理规则

| 条件 | 动作 |
|------|------|
| feature/fix 分支已合并到 test 且测试通过 | 迭代完结时删除 |
| feature/fix 分支已合并到 release | 迭代完结时删除 |
| test 分支 | 迭代完结时删除 |
| release 分支 | 合回 main 并打 tag 后删除 |
| 废弃分支（需求延期/取消） | 迭代完结时删除 |
| 未合并的 feature/fix 分支 | 通知开发者确认后删除 |

## 9. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| Codeup API 不可用 | 分支操作失败 | 加入重试机制（3次重试），失败后降级为人工操作并通知 |
| 自动合并导致代码质量问题 | 测试环境不稳定 | test 分支仅用于测试，release 分支逐个合并已验证代码 |
| 多人同时解决冲突 | 冲突反复出现 | 加锁机制，同一时间只处理一个分支的合并 |
| 开发者直接在 test/release 分支上提交 | 分支管理混乱 | 通过 Codeup 分支保护规则禁止直接 push |
| 迭代版本号命名冲突 | 分支名重复 | 创建前校验，版本号全局唯一 |

## 10. 实施阶段建议

### 阶段一：基础分支管理

- 迭代创建时自动创建 release/test 分支
- 工作项关联迭代时自动创建 feature/fix 分支
- 分支信息回填到云效工作项字段

### 阶段二：自动合并

- 云效提测 webhook → 自动合并到 test
- 合并冲突钉钉通知
- 冲突解决后自动重试

### 阶段三：发布与收尾

- 发布时从 feature 逐个合并到 release
- 迭代完结时打 tag、清理分支、合回 main

### 阶段四：增强

- Hotfix 流程
- 多迭代并行的自动同步
- 分支操作审计日志
- 分支保护规则自动配置

## 11. 待确认事项

1. **代码仓库对应关系**：一个产品线对应几个代码仓库？每个仓库都需要独立管理分支吗？
2. **云效字段**：用于存储分支名的云效自定义字段是否已创建？字段名是什么？
3. **Codeup 权限**：系统 API Token 是否有创建/删除分支和 tag 的权限？
4. **分支保护规则**：是否需要系统自动配置 Codeup 的分支保护规则（禁止 force push、要求 code review 等）？
5. **流水线集成**：测试环境和发布的流水线是否已经支持通过分支名触发？
6. **并行迭代上限**：同一产品线最多允许几个迭代并行？
